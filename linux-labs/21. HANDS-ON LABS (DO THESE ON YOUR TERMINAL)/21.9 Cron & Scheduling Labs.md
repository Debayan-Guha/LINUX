**How Crontab Scheduling Works**

A single `crontab` file can hold **dozens or hundreds of different scheduled tasks** simultaneously.

**Core Concepts**
*   **One File per User**: Every user account on a Linux system gets exactly one personal crontab file managed by the system.
*   **One Line per Job**: You simply add a new line to that single file for every new task you want to schedule.
*   **Independent Schedules**: Each line can point to a completely different script and run on its own independent timetable.

## 21.9.1.11 How Completed Cron Jobs Are Handled

When a scheduled job finishes running, **it is not automatically deleted** from the crontab file. 

For example, if you configure a job to run only on Monday the 19th at 5:00 PM, the system will execute the task at that exact time. Once completed, the entry will permanently remain in your crontab file until you manually open the file and remove it.

**Automating the Deletion**

If you need a job to be removed automatically after it finishes, you have two main options:
- **Self-Deleting Script**: You can append a command to the end of your cron line that automatically edits the crontab file to remove itself once execution finishes.
- **Alternative Tools**: For tasks that only need to run exactly once, using the system's built-in `at` command is generally safer and more efficient than using `cron`.

`/etc/cron.daily` is a predefined system directory in Linux. Any script or executable file you place inside it will automatically run **once every day**.

**Key Rules for Using cron.daily**
*   **No Cron Syntax Needed**: You do not write lines of asterisks (`* * * * *`). You just place a regular, executable shell script directly into the directory.
*   **Root Permissions Required**: Because this is a system-wide directory, you must use `sudo` to add or modify files inside it.
*   **Must Be Executable**: Your script will be ignored unless you give it execute permissions using `chmod +x`.
*   **Strict Naming Rules**: Script names must **not** contain periods (`.`) or extensions like `.sh`. Use `myscript`, not `myscript.sh`.

**Related Predefined Directories**

Linux includes several of these folders out of the box to make scheduling simple:

| Directory | Execution Frequency |
| :--- | :--- |
| `/etc/cron.hourly` | Runs once every hour |
| `/etc/cron.daily` | Runs once every day |
| `/etc/cron.weekly` | Runs once every week |
| `/etc/cron.monthly` | Runs once every month |

**1. What Exact Time Do They Run?**

Unlike a personal user crontab, you do not choose the exact minute these directories run. The system controls the timing using a master file called `/etc/anacrontab`. 

On most systems, daily scripts execute early in the morning (usually between **6:00 AM and 7:30 AM**), or immediately after the computer boots up if it was powered off during the scheduled time.



## 21.9.2.4 Check cron logs: `sudo tail -f /var/log/syslog | grep CRON`

This command monitors your system logs in real time and filters the output so you only see messages related to background cron jobs.

Running `sudo tail -f /var/log/syslog | grep CRON` serves as your primary diagnostic tool for confirming that your cron jobs are executing, tracking the exact timestamps of their runs, and verifying the specific system user responsible for triggering them. However, because this command only displays lifecycle events from the system logger, it cannot show the actual internal output or granular error data of your script. To understand the definitive result of the job—such as whether it ended in absolute success or suffered a script failure—you must separately examine the dedicated log file where you explicitly directed the command's standard output and error streams.

## 21.9.2.9 Create lock file mechanism using `flock`
<img width="913" height="680" alt="image" src="https://github.com/user-attachments/assets/b1a88acd-426c-419d-a419-b3d0a9b153bc" />


**Understanding Cron Job Overlap and Parallel Execution**

Cron runs all scheduled jobs at the same time in parallel. The wrapper script is only needed when the **same** job might start again before finishing. 

**The Overlapping Job Problem**

To understand why this matters, consider a cron job scheduled to execute **every 10 minutes** (using the `*/10 * * * *` syntax). 

*   **12:00 PM**: The first instance of your script starts running. It encounters heavy network traffic or a large data backlog, causing it to run slower than usual.
*   **12:10 PM**: Ten minutes have passed, but the first instance **has not finished yet**. 
*   **The Conflict**: Because cron operates on a strict clock and does not check if previous tasks are still alive, it will blindly launch a **second instance** of the exact same script right alongside the first one.

**Why This Is Dangerous?**
When two instances of the same script run simultaneously, they will compete for the exact same files, databases, or system resources. This overlap often leads to corrupted log files, duplicate database entries, server memory spikes, or infinite hanging processes.

**The Solution: Built-In Locking vs. Custom Wrapper Lock**

To prevent this overlap, you have two primary choices: you can use the system's built-in `flock` command directly in your schedule line, or you can write your own custom lock handling directly inside your script.

- **Option 1: Built-In System Tool (`flock`)**

This tool forces cron to check for an active file lock before executing. If the previous 10-minute task is still working, the new instance will safely exit immediately without causing an overlap:

```bash
*/10 * * * * flock -n /tmp/my_script.lock /usr/local/bin/my_script.sh
```

**How the Inbuilt Flock Command Works?**

For `flock` to work, you must provide it with a dedicated file path that acts as a central checkpoint. The utility uses this temporary file as a physical marker to track whether a script is actively running or idle. 

When a job triggers, `flock` inspects this file path; if the file is unlocked or does not exist yet, the utility automatically creates it, applies an exclusive lock flag via the Linux kernel, and lets your script run safely. If a duplicate job attempts to start while that flag is still active, `flock` recognizes that the checkpoint is busy and instantly cancels the new instance to prevent any parallel overlap.

**Unique Lock Files for Different Jobs**

It is crucial to note that **every individual scheduled job must have its own unique lock file**. 

Because `flock` relies strictly on the file path to determine if a task is busy, using the same lock file for different scripts will cause them to block each other. Assigning a distinct file name to each script ensures they can all run independently without unexpected interference:

**Task 1**: `flock -n /tmp/backup.lock /usr/local/bin/backup.sh`

**Task 2**: `flock -n /tmp/cleanup.lock /usr/local/bin/cleanup.sh`


- **Option 2: Custom Inside-Script Wrapper Lock**

If you want granular control—such as printing custom alerts when a collision happens—you can handle the lock manually by adding this validation block to the top of your actual script file:

```bash
#!/bin/bash
LOCKFILE="/tmp/my_script.lock"

# Check if the lock file already exists from a previous running instance
if [ -e "\$LOCKFILE" ]; then
    echo "Error: Previous 10-minute job is still running! Exiting to prevent overlap."
    exit 1
fi

# Create the lock file to claim this execution window
touch "\$LOCKFILE"

# --- Your Core Script Logic Runs Here ---
echo "Processing data window..."
sleep 15
# ----------------------------------------

# Clean up and delete the lock file so the next 10-minute cron can run
rm "\$LOCKFILE"
```
